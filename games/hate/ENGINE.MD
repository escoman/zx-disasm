# H.A.T.E. — как устроен движок рендеринга

Разбор сделан по дампу ОЗУ `$4000–$FFFF`, снятому на границе кадра, и по дизассемблеру
`asm/HATE_engine.asm`. Всё, что ниже помечено **[проверено]**, подтверждено двумя
независимыми способами: (а) чтением кода по адресу и (б) сверкой синтезированной
картинки с реальным экраном того же кадра. Помеченное **[гипотеза]** — рабочая модель
без полного подтверждения.

Скрипты, которыми это можно повторить, лежат в `tools/` (см. §10), картинки — в `render/`.

---

## 1. Главный вывод

Рендер H.A.T.E. — **не векторный и не спрайтовый**. Это тайловый конвейер на
клетках 8×8 пикселей, работающий через **цилиндрический (кольцевой) буфер**:

```
банк шаблонов $C400 (64 клетки по 8 байт)
        │
        ▼
кольцевой буфер $8000–$BFFF : «страница» = один столбец ландшафта из 16 клеток
        │                     (+ сдвинутая копия во второй половине страницы)
        ▼
список адресов экрана $D5B2 : заранее посчитанная «лесенка» (перспектива)
        │
        ▼
блиттер $D2E3/$D35E          : POP HL → 8 байт клетки вверх по экрану → DEC H
        │
        ▼
проход атрибутов $D338       : тот же список, второй раз, но как (столбец, строка)
```

«Трёхмерность» получается из двух вещей:

1. **Лесенка адресов.** Положение клетки на экране — не вычисление, а чтение готового
   списка `$D5B2`, где для каждого столбца экрана уже выписаны адреса клеток от дороги
   к горизонту. Это и есть перспектива: далёкие столбцы начинаются ниже и короче.
2. **Шаг `+$200−4`.** И при упаковке объектов, и при переходе от столбца к столбцу
   используется одна и та же арифметика: `H += 2; L −= 4` (адрес `+= $1FC`). В
   кольцевом буфере это «на две страницы вперёд и на 4 байта вверх», на экране — «на две
   строки ниже и на четыре байт-столбца левее». Отсюда наклон всех линий ландшафта.

## 2. Карта памяти

| Адрес | Что |
|---|---|
| `$4000–$5AFF` | экран |
| `$5800–$5AFF` | атрибуты |
| `$6000–$62FF` | таблица трассы/высоты: 24 × 32 байта **[проверено: читается LE3BF]** |
| `$6300` | шрифт, 96 глифов × 8 байт, MSB-первый |
| `$653A–$8008` | статический банк геометрии/объектов (6863 Б) |
| `$8000–$BFFF` | **кольцевой буфер ландшафта**: 64 страницы × 256 Б |
| `$C000–$C0FF` | записи объектов (16 × 16 байт) |
| `$C300` | таблица указателей на формы объектов (по 2 байта) |
| `$C32E` | номер текущей страницы кольца (0…$3F) |
| `$C32F` | половина страницы: `$00` = клетки, `$80` = сдвинутая копия |
| `$C400–$C5FF` | **банк шаблонов: 64 клетки 8×8** |
| `$C8EA` | таблица указателей на «части» уровня |
| `$CA43` | собранный список частей (то, что блиттер обходит) |
| `$C6xx` | записи столбцов ландшафта (15 кодов клеток подряд) |
| `$D5B2 …` | **список адресов экрана для блиттера**, 16-битные слова |
| `$F800` | буфер упаковки объектов (4 ряда × 21 Б и т.п.) |
| `$FE64`, `$FF00` | списки вывода объектов (код, число рядов, адрес, указатель формы) |

**Соглашение об именах меток:** в листинге `L<адрес>` — это сам адрес (`LDB60` = `$DB60`,
`LEFA5` = `$EFA5`). У подметок (`LDB60_34`, `LD4E9_4`) адрес в имени **не** закодирован:
`LDB60_34 = $DD47`, `LDB60_36 = $DD6C`, `LD4E9_4 = $D51D`, `LD2E3` = `$D2E3`,
`LD9D6` = `$D9D6`.

## 3. Ландшафт

### 3.1 Банк шаблонов `$C400` **[проверено]**

64 записи по 8 байт. Байт = 8 пикселей по горизонтали, запись = 8 строк. Код 00 —
пустая клетка (все нули), это «прозрачность»: блиттер всё равно её записывает, поэтому
клетка одновременно и стирает старое содержимое.
См. `render/01_pattern_bank_C400.png`.

### 3.2 Кольцевой буфер `$8000–$BFFF` **[проверено]**

64 страницы по 256 байт. Страница — это **один столбец ландшафта**, разложенный в 16
клеток:

```
+$00 … +$7F : 16 клеток по 8 байт = 128 байт (одна клетка = одна строка из 8 байт)
+$80 … +$FF : та же колонка, сдвинутая на 2 пикселя (см. §3.4)
```

Проверка: на кадре 1600 страницы `$90–$94` дают 16/16 совпадений с клетками банка,
например страница `$92` = `17 02 07 05 09 05 09 05 09 05 09 05 08 00 00 00`.
См. `render/02_ring_page.png`.

Кольцо — **скользящее окно**, а не копия экрана: видимый столбец экрана `x` начинается со
смещения `off(x)` внутри кольца, и `off(x+1) = off(x) + $1FC` (см. §3.7). Поэтому два
соседних столбца экрана берутся со сдвигом примерно в две страницы, а номер страницы
`($C32E)` задаёт точку, откуда кольцо «сейчас крутится».

### 3.3 Сборка страницы — `$D4E9` / `$D51D` **[проверено]**

`LD4E9_4` (около `$D51D`) собирает новую страницу, когда камера уходит на столбец
вперёд. Порядок:

1. `D = $80 + ($C32E)`, `E = $00` — указатель на текущую страницу.
2. Первые 8 байт — «специальная клетка»: из `$C4B8`, а если
   `((($C32E) >> 1) + 1) & 3 == 0` — из `$C4C0` (то есть у дороги есть 4 варианта
   ближней клетки, сменяемых по фазе).
3. Затем 15 клеток: `POP HL` (указатель из очереди `$CA43`), `HL += A` (смещение
   колонки), `code = (HL)`, источник `$C400 + 8*code`, `8 × LDI`.
4. Итого 128 байт = ровно 16 клеток.

То есть содержимое страницы — это «развёрнутый в кольцо» столбец уровня: коды берутся из
записи столбца (`$C6xx`, 15 байт подряд), а не рисуются.

### 3.4 Сдвинутая копия — `$D440`/`$D589` **[проверено кодом, применение — гипотеза]**

Вторая половина страницы (`+$80`) содержит ту же колонку, сдвинутую на **2 пикселя
вправо** побитовым сдвигом всего потока:

```
LD A,(DE) / LD C,(HL) / RL C / RLA / RL C / RLA / LD (HL),A
```

Это позволяет прокручивать ландшафт по горизонтали с шагом 2 пикселя, не пересобирая
страницу: `($C32F)` = `$00` даёт чётную фазу, `$80` — сдвинутую на 2 пикселя.
Нечётная фаза (1 пиксель) делается вариантом того же кода в `$D45B` (`RRA/RR C/RRA/RR C`).
Какую именно фазу выбирает игровой цикл в конкретный момент — **[гипотеза]** (на дампе
кадра 1600 `($C32F) = $00`).

### 3.5 Блиттер `$D2E3` / `$D35E` **[проверено]**

Самая «горячая» процедура кадра (в профиле кадра 1600 адреса `$D3C5–$D3E5`,
`$D38A–$D390` дают сотни попаданий).

```
LD ($C331),SP          ; сохранить свой стек
LD SP,$D5B2            ; СПИСОК АДРЕСОВ ЭКРАНА СТАЛ СТЕКОМ
...
POP HL                 ; адрес очередной клетки на экране
8 × (LD A,(DE); LD (HL),A; INC E; DEC H)   ; 8 байт вверх по экрану
```

Ключевые свойства:

* Источник `DE` идёт **подряд**: `E` увеличивается на каждый байт, `D` меняется между
  блоками. Поэтому 8 байт = одна клетка, а последовательные `POP` берут следующие 8 байт
  той же страницы.
* Запись идёт **вверх** по экрану: `DEC H` уменьшает `y&7`, то есть y уменьшается.
  Первый байт клетки попадает в **нижнюю** строку, восьмой — в верхнюю.
* Список — это и есть растеризация: `$D5B2` содержит 528 слов, по 2 байта на клетку;
  `$0800` в списке означает «писать в ПЗУ и забыть» (пустой такт, чтобы выровнять
  ритм), `$FFFF` — конец. Список заранее свёрстан как **лесенка**: для столбца 0 клетки
  идут от y=191 вверх до y=103, для столбца 24–31 — уже до y=7. Это и есть перспектива:
  чем правее столбец, тем он выше начинается.
  См. `render/03_terrain_silhouette.png` (красная сетка = клетки из списка).
* Адресация по страницам: `D = $80 + ($C32E) + (($C32F) & $7F)`, `E = ($C32F) & $FE`;
  между группами `D += 2; RES 6,D` — то есть две страницы вперёд с заворотом на
  `$80`/`$C0`. Стек-список и источник живут в разных «системах координат»: стек — экран,
  `DE` — кольцо.

### 3.6 Атрибуты — `$D338` **[проверено]**

Второй проход по тому же `$D5B2`, но слова читаются как пары `(L = столбец, A = строка)`:

```
LD A,(DE); LD L,A          ; байт 1 = столбец экрана
INC DE; LD A,(DE); INC DE  ; байт 2 = строка в «клеточной» нумерации
LD H,$58
CP $FF → RET               ; конец
CP $47 → меньше: пропустить (прозрачно)
CP $50 → H+1 → ...         ; $58/$59/$5A/$5B в зависимости от диапазона
LD (HL),B                  ; B = номер полосы/цвет
```

То есть цвет клетки задаётся не её кодом, а **полосой по вертикали**: по строке
выбирается одна из четырёх «дорог» атрибутной плоскости `$58`…`$5B`. Это объясняет,
почему один и тот же шаблон в разных местах дороги выглядит по-разному.

### 3.7 Ступенька: экран ← кольцо **[проверено]**

Если читать столбец экрана снизу вверх как поток байт

```
S(x) = scr(x,191), scr(x,190), …, scr(x,0)     (192 байта)
```

то он оказывается **непрерывным куском кольца**:

```
S(x)[n] = ring[( off(x) + n ) mod $4000]

off(x+1) = off(x) + $200 − 4   (mod $4000)
```

Измерено на кадре 1600: `off(31) = $9228`, далее шаг ровно `+508` на каждом столбце,
`off(20) = $BC54`, `off(22) = $804C` — арифметическая прогрессия с заворотом на `$8000`.
Совпадение байт в среднем **122 из 192 на столбец** (у «чистых» столбцов 137–149).

Шаг `+$1FC` = две страницы вперёд и 4 байта назад — это **ровно те же 2 страницы на
столбец**, которые видны в выводе объектов (§4.4: `page = $80 | (($C32E) + 2*band & $3F)`).
Отсюда и рабочая модель осей кольца:

* **номер страницы ↔ горизонтальное положение (глубина/столбец)**, две страницы на
  один байт-столбец экрана — 32 столбца × 2 = 64 страницы, всё кольцо;
* **байт внутри страницы ↔ высота на экране**, 1 байт = 1 пиксельная строка, чтение
  идёт вверх;
* сдвиг `−4` на столбец — уклон дороги: каждый следующий столбец ландшафта
  «приподнят» на 4 пикселя.

Остаток расхождения объясняется тремя вещами, и это важно для честности модели:

* HUD (панель `SCORE` занимает правый низ) и заголовок слева затирают часть столбца;
* объекты в кадре могут быть уже стёрты из кольца (см. §4.4), а на экране ещё видны;
* часть столбцов добирается с другой страницы (поток пересекает границу двух
  столбцов ландшафта).

Поэтому «идеального» восстановления всего экрана из кольца не получается — см.
`render/04_reconstruction.png`, где рядом стоят реальный кадр, восстановление только из
кольца и карта расхождений.

### 3.8 Подпиксельный скролл

`($C32E)` = номер страницы (столбец ландшафта), `($C32F)` = половина страницы
(`$00`/`$80`, то есть 0 или 2 пикселя горизонтально). `($D14D)` = пройденное
расстояние (на кадре 1600 = `$0354`), `($D14F)` = X камеры. Вертикальное смещение внутри
клетки получается автоматически: блиттер стартует с произвольного байта страницы, поэтому
клетки на экране не выровнены по 8 пикселей — именно из-за этого попытка «разложить
экран на клетки банка» даёт совпадение только для части клеток (§4.6).

## 4. Объекты

### 4.1 Записи объектов **[проверено фрагментарно]**

Таблица 16-байтных записей в `$C000–$C0FF` (16 штук). На кадре 1600 живая запись одна,
`$C0A0 = 01 00 06 2C 02 00 00 00 02 …` (тип 1, расстояние `$0600`, боковое `$2C`), а
остальные 15 помечены как «припаркованные» (`$80/$82/$83/$8B`). Поля, которые видны из
кода:

| Смещение | Смысл |
|---|---|
| `+0` | тип; `bit7` = запись свободна (`$80/$83/$8B` — «припаркована»), `bit6` = особый маршрут через `$F089`, `bit5` = **юнит уничтожен** (см. §4.7: ИИ и столкновения пропускаются, фаза принудительно 1, класс геометрии подменяется на `$03`), младшие 4 бита — номер формы |
| `+1,+2` | расстояние до объекта (16 бит) |
| `+3` | боковое смещение относительно оси дороги |
| `+4` | клиренс/высота |
| `+8` | индекс арта: `HL = слово по адресу $C300 + [8]` — **байтовое** смещение (`$DBE9 LD L,(IX+$08)` / `$DBEC LD H,$C3`). У живого юнита `[8] = 2*(тип & $0F)` (`$E2A1…$E2A4`); при гибели `$E4A9` пишет `$20`, и `$E238` прибавляет по 2 каждый кадр |
| `+9` | фаза ракурса 0…3 (пишется проекцией) |
| `+10` | X на экране (пишется проекцией) |
| `+11` | полоса/строка (пишется проекцией) |

### 4.2 Проекция `$EFA5` **[проверено]**

```
IX = $C000, шаг 16
BIT 6,(IX+0) → JR $F089        ; особые объекты — отдельная очередь
BIT 7,(IX+0) → пропустить      ; свободная запись
расстояние = ([1],[2]) − ($D14D)
HL = расстояние − [3] − 1      ; перевести в «клеточную» систему
отсечение: если старший байт ∉ {0,1} или L >= $1F — не рисуем
[11] = HL >> 3                 ; ПОЛОСА (band): расстояние в клетках;
                               ; $DB60_32 делает из неё страницу кольца:
                               ; page = $80 | (($C32E) + 2*[11] + $78) & $3F
[9]  = ((X − [3]) >> 1) & 3    ; ФАЗА РАКУРСА (4 варианта), при bit5 → 1
[10] = ($C32F) + [3] + $10 + фаза   ; смещение внутри страницы (вертикаль)
затем добавление в список ($EFA1) и, для типов ≥ $0E, во второй ($EFA3)
```

Обратите внимание: объект «прикрепляется» к **странице кольца** (через `[11]`), а не к
экрану, и его координата по второму измерению (`[10]`) попадает в байт внутри
страницы. Дальше патч кладётся в кольцо, и его выводит на экран тот же блиттер, что и
ландшафт. Отсюда правильная перспектива без единого умножения в кадре.

### 4.3 Размерные классы, фазы и таблица форм `$C300` **[проверено]**

Три класса по `[0] & $0F` (ветвления `$DA1E` / `$DAA1` / `$DB1B`):

| Тип | Патч | Ширина ряда | Шаг фазы |
|---|---|---|---|
| 0–3 | 4 ряда × 21 байт | `$15` | `$A8` = 168 |
| 4–$0A | 3 × 17 | `$11` | `$66` = 102 |
| $0B–$0D | 2 × 13 | `$0D` | `$34` = 52 |

Шаг фазы — ровно **2 × (рядов × ширина)**: 2·(4·21)=168, 2·(3·17)=102, 2·(2·13)=52.

Указатель на форму берётся из слова `$C300 + 2*(IX+$08)`, затем сдвигается на
`фаза × шаг`:

```
L = (IX+$08); H = $C3; A = (HL); INC L; H = (HL); L = A   ; HL = word at $C3xx
BC = $34 / $66 / $A8 ;  фаза = (IX+$09)-1 & 3
повтор: HL += BC           ; выбор из 4 фаз
```

То есть в банке `$653A–$8008` лежит по 4 ракурса на объект, а `$C300` — таблица
указателей на них. Патч описывается в координатах кольца: **ряды** — это шаги по
страницам (`+$1FC`), **ширина** — число байт внутри страницы.

### 4.4 Вывод объекта в кольцо: `$D9D6` ← `$DB60_32` ← `$DD44` **[проверено]**

Проекция `$EFA5` только заполняет записи. Сам вывод делает `$D9D6`: он обходит список
`$6500` (элемент = 2 байта адреса записи) и для каждой записи строит элемент списка
вывода в `$FF00` (`($DD68)` — курсор), сбрасывая курсоры: `($DD6A) = $F800` (буфер
упаковки), `($DD66) = $FE64` (второй список, помечается `$FF` как пустой).

```
IX = запись
type = (IX+0):  <$04 → класс «4 ряда» ($DA1E)
                <$0B → класс «3 ряда» ($DAA1)
                <$0E → класс «2 ряда» ($DB1B)
база = таблица[distance >> 1]      ; $5FF6 + dist/2  (для 3-рядов: $5FF7)
                                   ; это та же таблица трассы $6000–$62FF
x    = (база) & $1F + (IX+$0A)     ; младшие 5 бит байта трассы + X записи
                                   ; (+2 для класса «3 ряда»)
band = (IX+$0B)
```

Дальше `band` разбирается на **число рядов и вариант обрезки**: `band−4` сравнивается с
`$1D`, `$1E`, `$1F` (объект уходит за дальний край: 4/2/1 ряд) и с `$FD`, `$FE`, `$FF`
(за ближний: база сдвигается на `$44`/`$22`/`$1A`, адрес кольца — на
`$1F8`/`$FC`/`$FC`). Если фаза `(IX+$09)` равна 0, число рядов уменьшается на 1;
если и оно стало 0 — объект не выводится.

Кульминация — общий хвост `$DB60_32`, где считается адрес в кольце:

```
A = ($C32E) + 2*band + $78
D = $80 | (A & $3F)        ; RES 6,D / SET 7,D — страница с заворотом кольца
E = x                      ; байт внутри страницы
```

Элемент списка (8 байт в `$FF00`): `[0]` код формы (`$11` — 4 ряда, `$0F` — 3 ряда,
`$0D` — 2 ряда), `[1]` число рядов, `[2..3]` адрес в кольце (`E`,`D`, он же копируется
в `($D9D4)`), `[4..5]` указатель формы.

После построения списка:

* `$DD44` (`LDB60_33`): `HL = ($D9D4)` — адрес в кольце, `DE = ($DD6A) = $F800` —
  буфер: `LDIR` по рядам **снимает фон** из кольца в `$F800`. Ширина ряда — `A`
  (`$15/$11/$0D` = 21/17/13), после каждого ряда `L −= 4; H += 2; RES 6,H` —
  шаг `+$1FC` с заворотом, тот же, что и на экране.
* `$DD6C` (`LDB60_36`): `($DD6A) = $F800`, обход `$FE64`, и запись рядов **обратно
  в кольцо** с тем же шагом (`LDB60_46`).

То есть кадр устроен как «снять фон → пересчитать → положить объект заново»:
поэтому к моменту, когда изображение уже на экране, в кольце объекта может не быть.
Важное следствие: и объекты, и ландшафт — это одни и те же 8-байтовые клетки,
и они складываются в одну и ту же адресную сетку кольца.

### 4.6 Разложение объектов на клетки **[проверено с оговоркой]**

Если разрезать видимый объект на клетки 8×8 и искать каждую в банке `$C400` (с точностью
до вертикального сдвига 0…7 строк), находится **ближайший** код, но точного совпадения
почти нет: на экране клетка смещена на несколько строк относительно границ банка
(§3.8). Коды при этом кучкуются в узком диапазоне (`$3E`, `$3F`, `$3D`, `$2B`, `$27`,
`$2D`, `$0D`), то есть объект действительно собран из того же набора шаблонов, а не
нарисован отдельным спрайт-шитом. Ошибка — в 1–2 строки, что и даёт сдвиг.

### 4.7 Рендер юнита: замкнутая и побайтово проверенная модель **[проверено]**

Это финальная версия: предыдущие попытки (§4.5/§4.6, «векторный конвейер» в README)
были неверны. Юнит — это обычный AND/OR-спрайт из банка, только лежит он не в
координатах экрана, а в координатах **кольца**, и потому попадает в перспективу
бесплатно.

**Порядок внутри прохода** (важно: он обратный тому, что предполагалось):

```
$D9D6   собрать списки $FE64/$FF00; $DD44 LDIR кольцо->$F800  (СНИМОК фона)
$EAE3   композит: A = (DE) & (HL) | (HL+1); (DE) = A         (юнит В Кольцо)
$D35E   блит кольцо -> экран                                 (вот он, кадр)
$D3F2   LD SP,($C331)
$D3F6   CALL $DD6C  -> LDIR $F800->кольцо                     (ФОН обратно)
```

То есть кольцо в момент `$D3F2` — это ровно то, что этот же проход кладёт на экран.
Никакой задержки «на 4 кадра» нет; расхождения прежних попыток были вызваны
неверной обратной формулой адреса экрана (строки идут `+256`, а не `+32`):

```
экран($4000 + o):  o = ((y>>6)&3)*2048 + (y&7)*256 + ((y>>3)&7)*32 + x
```

**Формат элемента `$FF00`** (6 байт): `[0]` класс, `[1]` число столбцов, `[2..3]`
адрес в кольце, `[4..5]` указатель на форму. Класс → ширина строки формы:
`<4 → $15(21)`, `<$0B → $11(17)`, иначе `$0D(13)`; у `$FE64` своя таблица
(`<4 → $11`, `<$0B → $0B`, иначе `$04`), потому что там восстанавливается фон.

**Формат формы** — `count` столбцов по `width` пар (AND-маска, OR-значение),
столбцы подряд, шаг столбца `2*width`. Нулевой ряд банка = **нижний** ряд спрайта.
Столбцы спрайта кладутся в кольцо с шагом `$1FC` = «+2 страницы, −4 ряда»: это ровно
компенсирует наклон блиттера, поэтому юнит стоит вертикально.

**Указатель формы**: `HL = слово по адресу $C300 + [8]` (именно байтовое смещение,
`[8]` — не номер строки таблицы), затем `+ (([9]-1)&3) * шаг`, шаг =
`2*(рядов*width)` = `$A8`/`$66`/`$34`. Проверено на записях `$0B`/`$0C`
(`[8]=$10` → база `$7878`; `[9]=2` → `$78DE`, `[9]=0` → `$79AA`).

**Кто есть кто.** Запись `$C000` (индекс 0) стоит в **одной и той же точке экрана**
от прохода к проходу — это техника игрока (камера следует за ней). Остальные записи
за те же проходы уезжают по экрану — это враги и предметы.

**Класс элемента = вид юнита.** Выбор арта игрока делает `$D21B…$D246`:

```
$D22B  LD HL,($CF2E)   ; дескриптор сцены
       LD DE,(HL)      ; -> байт вида техники
$D233  LD ($C000),A    ; запись 0 = игрок, тип = этот байт
$D23C  INC A / AND $01
       LD ($C0A0),A    ; тот же выбор, но со сдвигом, в тип записи 10
$D242  AND $0F / ADD A,A
$D246  LD ($C008),A    ; [8] = 2*kind, то есть база формы = $C300 + 2*kind
```

То же самое движок делает для **всех** записей, не только для игрока: `$E2A1 LD A,(тип) /
AND $0F / ADD A,A / $E2A4 LD (IX+$08),A` держит `[8] = 2*(тип & $0F)`, а класс элемента
`$FF00` — это ровно тот же `тип & $0F` (`$DBC0 LD A,(IX+$00)` → `$DBD6 AND $0F` →
`$DBD8 CP $04 / $DBDC CP $0B`). Значит таблица `$C300` — это **16 видов техники**, а не
«три ширины спрайта»: один и тот же полубайт задаёт и арт, и геометрию
(`kind<4 → 4×21`, `kind<$0B → 3×17`, иначе `2×13`).

Исключение — **гибель**. `$E4A1`/`$E4E7`/`$EBE2` ставят типу бит 5 и пишут `[8]=$20`,
`$E238…$E242` прибавляет по 2 каждый кадр, а на `$2D` (`$E23A CP $2D`) запись освобождается
через `SET 7` — это 7 кадров `$20,$22,$24,$26,$28,$2A,$2C` = индексы 16…22 таблицы. Пока
бит 5 стоит, `$DBC5…$DBD4` **подменяет класс на `$03`** (самая широкая рамка 4×21 — под
обломки нужно больше места), `$E194` обходит ИИ, `$E44C` — проверку столкновений, а `$F01A`
форсирует `[9]=1`, поэтому взрыв всегда смотрят с одного ракурса. На шагах `$22` и `$28`
ветка `$E250…$E2A4` (её проходят только классы 0 и 1, то есть техника игрока) снимает
элемент из очереди `($ECF1)`/`($ECE5)` и запускает по нему ту же анимацию — из гибели
игрока вырастает второй объект. Обратный сброс — `$E29C RES 5,A` и пересчёт `[8]`.

| kind | база | байт | что это |
|---|---|---|---|
| 0 | `$6580` | 630 | **самолёт игрока** — воздушные миссии |
| 1 | `$67F6` | 630 | **танк игрока** — наземные миссии (корпус + башня + ствол) |
| 2 | `$6A6C` | 630 | наземный враг: клиновидная машина |
| 3 | `$6CE2` | 630 | купол/турель на основании |
| 4 | `$7416` | 374 | вспышка (звезда) |
| 5, 6 | `$758C` | 374 | гриб взрыва (у 5 и 6 общая база) |
| 7 | `$7702` | 374 | гриб на ножке |
| 8, 9 | `$7878` | 374 | **летающий враг** — та «птичка», что была на `31_unit_enemy.png`; у 8 и 9 общая база |
| 10 | `$72A0` | 374 | куб |
| 11 | `$79EE` | 182 | колонны/ворота |
| 12 | `$7AA4` | 182 | мелкий снаряд (штрих) |
| 13 | `$7B5A` | 182 | мелкий снаряд (шар) |
| 14 | `$6F58` | 420 | в `$FF00` не встречался; для класса `>= $0E` в `$DBE1…$DBE6` отдельная ветка, своего слота в порядке адресов нет |
| 15 | `$70FC` | 420 | то же |
| 16…22 | `$7C10…$7F58` | 6×168 | **общая анимация гибели**: 7 шагов индексов (`$20` и `$24` дают одну и ту же базу `$7CB8`) = 6 кадров «шар → плоские обломки», шаг `$A8` до конца страницы `$7FFF` |

**Доказательство, что класс и индекс арта — одно число.** Область вида `k` простирается
от `база(k)` до следующей базы, и её размер ровно равен максимальному разбросу
указателя: `3*шаг + (cols-1)*2*width` = 630 / 374 / 182 байт. Проверено для всех
баз таблицы 0…13 — области идут **впритык**, без щелей и наложений, то есть каждому
классу выделен ровно его набор фаз (у 14 и 15 регион 420 — они и не рисуются).
Плюс сверка на двух длинных прогонах
(`tools/unitsweep.py`, кадры 1400–12000 и 12000–30000: 4492 прохода, 192 уникальных
спрайта): `width`/`cols` каждого элемента совпадают с геометрией его класса без
исключений, и каждый указатель лежит внутри своего региона. За регион выходят только
20 указателей — все у класса `$03`, и это ровно `$7C10…$7F58`, анимация гибели.
В геймплее встретились классы `00 02 03 04 06 08 0A 0C`; индексы 1 (танк игрока),
5, 7, 9, 11, 13, 14, 15 за эти проходы не рисовались ни разу.

И ещё одна независимая сверка: живой дамп страницы `$4000–$7FFF`, снятый на `$D3F2`, и
ранний `data/gfx/bank_653A.bin` (6863 байта, «статичный банк геометрии») совпадают
**побайтово на всём протяжении `$653A–$7FFF`**, 0 расхождений. То есть каталог на
`35`/`36` нарисован из того же банка, что был извлечён совсем другим способом.

**Вид игрока.** Дескрипторы 10 сцен лежат в таблице `$CF04` (10 записей по 4 байта,
terminator `$FFFF`), и байт вида в них чередуется `00,01,00,01,…` — то есть половина
сцен отдаёт игроку самолёт, половина — танк. Порядок обхода сцен (какая из них
миссия с номером N) здесь не проверялся. Режим `--kind 1` в `tools/units.py` (пишет
`$C000=1` и `$C008=2`) заставляет запись 0 рисоваться как `cls=01 ptr=$67F6` ровно в
том же фиксированном слоте, а `unit_shot` подтверждает 84/84 байт по реальному кадру —
это танк игрока. Каталог всех видов: `render/34_player_forms.png`,
`render/35_unit_kinds.png`. Запись 10 в этом прогоне не рисовалась ни разу.

**Оговорка к прежнему тексту.** Здесь раньше было написано, что смена арта в слоте
игрока (`$6A6C`, потом `$7C10…$7F58`) — это «трансформация». Неверно:
`$7C10…$7F58` — хвост той же таблицы, и его проигрывает **любая** запись, ушедшая в
состояние `$2X` (тип `08→28` у врага, `00→20` у игрока), после чего враг из таблицы
исчезает; `$6A6C` — вид 2, к игроку отношения не имеет. Теперь этот механизм разобран
полностью: `$E4A9`/`$EBF0` пишут `[8]=$20`, `$E238` добавляет по 2, `$E23C` на `$2D`
освобождает запись, а `$DBD4` на это время подменяет класс на `$03`.

**Точность модели.** Все байты под юнитом совпадают с экраном побитово
(84/84, 34/34, 51/51, 22/22 — «не совпало с реальным кадром 0»). Предсказание
`(фон & маска) | значение` расходится на несколько байт, и **всегда это байты с
маской `$FF`**, то есть прозрачные: снимок фона `$DD44` успевает устареть, потому что
под спрайтом ландшафт перерисовывается. На сам спрайт это не влияет.

Инструменты: `tools/units.py … --bank [--kind N]` (перехват прохода + дамп банка
того же прохода + смена вида игрока), `tools/unitsweep.py` (перепись всех спрайтов
за долгий прогон, с экраном и записями), `tools/kinds.py` (каталог видов из дампа
страницы; `--sweep` помечает нарисованные, `--all` добавляет анимацию гибели,
`--colour` берёт реальные чернила/бумагу), `tools/sprite_strip.py` (плёнка спрайтов
по проходам),
`tools/bankdump.py`, `tools/unit_shot.py` (4 панели: спрайт / экран / маска-значение
/ модель), `tools/frame_png.py`, `tools/shot.py`.

## 5. Уровень и дорога

* `$C8EA` — таблица указателей на «части» уровня; из неё собирается очередь `$CA43`,
  которую выедает `$D51D` при сборке страницы (§3.3).
* Запись столбца ландшафта — 15 байт кодов клеток подряд (`$C6xx`, шаг 15 или 18 байт
  в зависимости от таблицы).
* `$6000–$62FF` — таблица трассы: 24 × 32 байта (высота/проходимость по столбцу).
  Её читает `LE3BF` — скан клиренса для ИИ и для проверки «можно ли ехать».
* Дескриптор сцены — по указателю `($CF2E)`.

## 6. HUD и панели

### 6.1 Панели — это не рендер, а статичный образ экрана

Панель приборов (левый верх: логотип + сегментная шкала) и панель счёта
(правый низ: SCORE/MAX/HIGH) **движком не рисуются**. Это кусок готового
экранного образа, который лежит в кольце:

| | |
|---|---|
| bitmap | `$A000–$B7FF` (6144 Б) |
| атрибуты | `$B800–$BFFF` (768 Б) |
| артефакт | `data/gfx/hud_panels.scr` (6912 Б), снимается `tools/panel.py dump` |

Образ в `$A000` кладёт RLE-разворачиватель `$5B8C` (escape `$97`; счётчик с
битом 7 — N нулей, иначе N повторов предыдущего байта; источник `HL=$E9F6` идёт
вниз до `$5FB3`, приёмник `DE=$FFFF` тоже вниз), то есть панель приезжает с
диска внутри INXS+RLE-кучи и никогда не пересобирается.

Выгрузка образа на экран — самомодифицируемый став в кольце, который пишется на
лету (в обоих skool-ах эти адреса записаны как `DEFB`, потому что к моменту
снятия ctl там уже рельеф):

```
$9F1C DI
$9F1D LD HL,$A000     ; bitmap образа
$9F20 LD DE,$4000     ; экран
$9F23 LD BC,$2000     ; картинка + атрибуты с хвостом
$9F26 LDIR            ; <<< этот PC дают все события трассировки
$9F28 XOR A / LD ($C2F8),A / JP $C2B1
```

Перед ним тот же став делает `$7C00 → $6300` (`$2400` Б), `CALL $EE17` со
строкой `$9F2F` («HOSTILE-ALL-TERRAIN ENCOUNTER»), `CALL $9F4B` и `CALL $8000`.

### 6.2 Почему панели не затираются рельефом

Блиттер `$D35E` за проход восстанавливает на экран **диагональный клин**, а не
весь кадр. Замер `tools/hud3.py` (экран заранее залит маркером `$5A`, дальше —
сколько байт вернул каждый проход), кадр 2000:

* окно субтитров (`$D9D6`) возвращает 54 байта — строка 6, колонки 2..7;
* обход HUD, композит юнитов и вход в блит — **0 байт**;
* сам блит возвращает 3792 байта (485 клеток клина);
* **2304 байта = 299 клеток не возвращает ни один проход** — это ровно левый
  верхний и правый нижний треугольники, то есть обе панели.

Доказательство на картинке: `render/39_hud_blindspot.png`. Значит панель
рисуется один раз при сборке меню (кадры 1235–1237) и живёт в экранной памяти
всю сцену. `tools/panel.py when` на всём прогоне 0..2100 даёт ровно один
всплеск изменений в этих треугольниках (>60 байт) — тот же переход заставка →
меню; в геймплее меняются только 9 клеток мигающей диагональной рамки.

### 6.3 Сверка образа с игровым экраном

`python3 tools/panel.py dump tmp/probe_play.txt 100 2000 tmp/x.scr`: из 299
клеток панелей **286 совпадают побайтно** с образом `$A000` (на кадрах 100 и
1240 образ идентичен). Расходятся 13:

* 9 клеток рамки (`$57 ↔ $A8/$AB`) — мигание;
* `(22,18)` — сегменты шкалы, `(29,20)`/`(29,21)` — цифры SCORE/MAX,
  `(29,23)` — значение HIGH; их поверх образа кладёт оконный движок.

Палитра атрибутов панелей: `$02` (чёрный/красный), `$06` (чёрный/белый),
`$10` (красная бумага), `$03` (чёрный/маджента), `$07` (чёрный/яркий белый),
`$38` (белая бумага — поле разрядов), `$15` (циан по красному — сегменты шкалы).
«Зелёный» на скриншоте — это как раз cyan `$15`.

### 6.4 Что всё-таки рендерится: обход списка `$FE64`

Узкие полоски индикаторов — масочный конвейер, разобран в `tools/hud.py` и
подтверждён побайтово. Запись списка 8 байт:

```
[0] класс  [1] режим E  [2..3] BC — поток дескрипторов
[4] число рядов  [5] стартовая колонка скретча  [6..7] назначение
```

* голова `$DDED`: `A=(HL)`, `CP $FF`, `JP Z,$EAE3`; `E=rec[1]`, `BC=rec[2..3]`;
  класс < 4 → широкий plotter `$DE08`, класс < `$0B` → узкий `$DF0F`, иначе `$E008`;
* plotter обнуляет скретч `$6500` (`LD D,$44` = 4×17 байт для широкого,
  `LD D,$21` = 3×11 для узкого) и набирает из шаблонов программу
  `LD D,n / CALL $E0xx`; база шаблонов по классу — широкие
  `$5DE8`/`$5EF0`/`$5CE0`, узкие `$5B60`/`$5C60`/`$5BE0`; режим E добавляет
  смещение (широкие 0/`+$40`/`+$83`/`+$C7`, узкие `+$40`/`+$60`/0/`+$20`);
* blit `$DECB` (широкий, **17 байт в ряду**) и `$DFAA` (узкий, **11 байт в
  ряду**): `LD A,(DE) / AND (HL) / LD (HL),A`; шаг назначения
  `DEC L×4, INC H×2, RES 6,H` = `+$1FC` с заворотом по кольцу; скретч по рядам
  идёт подряд (`$6500+17k`, `$6500+11k`), потому что `DE` не сохраняется
  `PUSH/POP HL`.

В геймплейном кадре в списке ровно две записи: `$FE64` класс `$08` режим 2,
`BC=$60D4`, 2 ряда, назначение `$9BBC`; `$FE6C` класс `$00` режим 1, `BC=$6072`,
4 ряда, назначение `$ABBD`; терминатор `$FF` на `$FE74`. **Композиция идёт
только в кольцо — экран за весь обход не меняется ни на байт**, а в клетки
панели значение попадает лишь там, где их накрывает клин блиттера.

### 6.5 Текстовые окна

Оконный движок `$EDCA`/`$EE17`, структуры окон `$F0EB`/`$F12C`, шрифт `$6300`
(96 глифов × 8 байт, MSB-первый, индекс = код − `$20`), строковый банк
`$F0E4–$F1A4`. Код символа с битом 7 = разрыв строки, `$FF` = конец окна.
Сюда же попадают цифры SCORE/HIGH и строка субтитров на 6-й строке.

## 7. Порядок кадра

Восстановленный по трассировке порядок для игрового кадра (уточнён §4.7 —
композит юнитов идёт **до** блита, а снятие/восстановление фона оплетает блит
снизу и сверху):

1. `$D050` — логика/ввод/статус, при необходимости — смена сцены.
2. `$EFA5` — проекция объектов; `$D9D6` строит списки `$FE64`/`$FF00`,
   `$DD44` снимает фон в поток `$F800`.
3. `$EAE3` — композит юнитов **в кольцо** (`(ring & mask) | value`).
4. `$D2E3`/`$D35E` — **блит ландшафта+юнитов** кольцо → экран (основное время кадра).
5. `$D338` — атрибуты по тому же списку.
6. `$DD6C` — восстановление фона из `$F800` (кольцо снова чистый ландшафт).
7. `$EDCA`/`$EE17` — окна и текст HUD.
8. `LE3BF` — скан трассы (для ИИ/клиренса), обычно раз в несколько кадров.

Порядок подтверждён трассой `tools/hud.py --walk` на кадре 2000; реально на
кадр обхода приходится такой набор точек останова:

```
$D3F2 -> $EE17 (HL=$F136) -> $D9D6 (HL=$6508, DE=$FF08) -> $DDED
  -> $DF0F (узкий plotter) -> $E06B $E075 $E084 $E08E $E09D $E0A7 $E0B6
  -> $DFAA (узкий blit) -> $DDED
  -> $DE08 (широкий plotter) -> $E0EE $E0F8 $E107 $E118 $E127 $E0C6 $E0D5
  -> $DECB (широкий blit) -> $DDED (класс $FF) -> $EAE3 -> $D35E -> $D3F2
```

Блит и проход объектов выполняются раз в 4 кадра; `$C32F` чередует `00`/`$80` на
каждом проходе, `$C32E` растёт на 1 раз в два прохода.

Точная последовательность вызовов внутри `$D050` пока проверена не полностью —
см. §8.

## 8. Что осталось непонятным

1. **Поразрядная раскладка форм.** ~~Закрыто в §4.7~~: форма — это `count` столбцов
   по `width` пар (AND,OR), столбцы в кольце с шагом `$1FC`, ряд 0 банка = нижний.
   Проверено побайтово на реальном кадре.
2. **Когда и насколько проворачивается кольцо.** Шаг страниц на столбец (`+2`) и
   база `$78` измерены; момент перекрутки (`($C32E)` через 64 страницы) в трассе
   не пойман.
3. **Роль `$D105`.** Старый README называл `$D105–$D150` «растеризатором сегментов».
   В профиле кадра 1600 этот код в горячем пути не участвует; вероятно, это ветка для
   другого режима (заставка/меню/особые сцены) либо ранняя версия. Требует отдельной
   трассировки по кадрам меню.
4. **Сколько объектов реально проецируется в кадре.** В геймплее (кадр 2004) — две
   записи рисуются списком `$FF00` (игрок + враг), в демо — до восьми. Крупные
   «камни/плиты» на экране — это клетки ландшафта из `$C400`, а не объекты; вопрос
   закрыт наблюдением в §4.7.
5. **Техника игрока в других формах.** ~~Закрыто в §4.7~~: игрок — это вид 0
   (самолёт, база `$6580`) или вид 1 (танк, база `$67F6`); выбор делает `$D21B…$D246`
   из байта дескриптора сцены, в 10 сценах он чередуется `00/01`. Танк подтверждён
   прогоном с `--kind 1` и побайтовой сверкой `unit_shot` (84/84).
6. **Отрисовка главного меню и демо-режим.** ~~Частично закрыто в §6~~: панели
   меню и игрового HUD — один и тот же статичный образ `$A000` (§6.1), а меню —
   он же плюс текст окон. Не разобрано: чем собирается жёлтый рельеф фона меню
   и как именно образ попадает в `$A000` из кучи INXS (сам RLE-став `$5B8C`
   описан в `data/gfx/GFX_NOTES.md`).
7. **Демо-режим.** Отложен по времени: отдельного прохода по демо-кадрам не делалось.

## 9. Поправки к README

В `README.md` (раздел 4) написано: «векторный (wireframe) конвейер, спрайт-шитов нет …
растеризатор `$D105–$D150` рисует сегменты как арифметическую прогрессию адресов».

По коду и по данным кадра это верно лишь отчасти:

* «спрайт-шитов нет» — **верно**: отдельных спрайтов действительно нет, всё
  упаковано в общий банк шаблонов `$C400`;
* «векторный конвейер» — **неверно**: картинка складывается из клеток 8×8, узор
  берётся из `$C400`, а перспектива — из заранее посчитанного списка адресов `$D5B2`,
  а не из растеризации отрезков в кадре;
* «арифметическая прогрессия адресов» — **верно** и подтверждено: это шаг `+$200−4`
  (`+$1FC`) и по столбцам экрана, и при копировании рядов патча;
* `$D105` в игровом кадре не участвует, его роль требует отдельной проверки.
